### 当前施工：1-4-3. SQLite StateStore、ArtifactStore与loopback Relay

StateStore、credential、ArtifactStore与Relay持续施工：StateStore已具备Human-owned network、network-level CAS append/read、dedupe/conflict、canonical hash、snapshot revision与原生HTTPS读写；SQLite credential provider已实现opaque token、hash存储、scope、expiry、revoke与真实mTLS HTTP授权链路；content-addressed ArtifactStore已实现sha256 artifact、不可变metadata、幂等put、network归属与完整性校验；Relay contract已固定session/lease/attempt、at-least-once、accepted-before-ack、bounded retry、revoke/恢复/状态机语义；loopback Relay HTTP adapter已实现healthz、免认证readyz依赖探针、mTLS node_id、protocol negotiation、credential-bound session TTL、authenticated non-sensitive status、session close、认证long-poll空结果204、受限delivery envelope 200响应（仅返回引用与元数据，不携带业务payload），以及注入式delivery ack：成功表示transport acknowledged，过期lease映射410，冲突映射409。npm run test:agent-local 82/82通过。仍未实现credential issuance HTTP/Human UI、ArtifactStore HTTP与双Agent端到端fixture。

**决策：**
- Q: SQLite StateStore、ArtifactStore与loopback Relay的施工顺序是什么？ → 采用先SQLite-compatible StateStore，再ArtifactStore，最后loopback Relay。StateStore先钉住身份、授权、生命周期、幂等与CAS canonical facts；ArtifactStore随后承载不可变验证产物；Relay最后依赖前两者提供认证、投递与恢复事实。 (Human accepted this implementation order.)
- Q: SQLite StateStore首个真实provider采用什么驱动？ → 采用better-sqlite3作为首个真实provider；核心StateStore与EnrollmentRecordStore保持provider-neutral。better-sqlite3提供本地事务、WAL、CAS revision与幂等约束，未来可替换PostgreSQL-compatible managed provider。 (Human accepted better-sqlite3 for the first real local provider.)
- Q: SQLite StateStore的canonical schema采用什么形态？ → 采用单一append-only state_events表作为canonical facts来源，字段包含network_id、event_id、aggregate_type、aggregate_id、event_type、revision、occurred_at、payload_json和created_at；enrollment、Graph、credential等通过typed projection adapter读取，不复制可变真相表。 (Human accepted the single event-log canonical schema.)
- Q: SQLite StateStore的revision与CAS作用域是什么？ → 采用network-level全局单调revision：每个network独立维护revision，append必须携带expected_revision，事务内匹配才写入revision+1；不匹配返回conflict，不覆盖、不隐式重试。event_id在network内唯一负责幂等dedupe，aggregate字段只用于查询与投影。 (Human accepted network-level CAS ordering.)
- Q: StateStore对业务层暴露什么API边界？ → 只暴露provider-neutral typed API：getRevision(network_id)、appendEvent(network_id, expected_revision, event)和readEvents(network_id, aggregate/after_revision)，append结果区分recorded、duplicate、conflict；业务层不直接依赖SQL，SQLite只存在provider内部。 (Human accepted the typed provider boundary.)
- Q: SQLite StateStore采用什么并发与持久化配置？ → 采用WAL、foreign_keys=ON、busy_timeout=5000、synchronous=FULL；append使用显式事务，CAS冲突不自动重试，由上层重新读取后决策；数据库目录由调用方提供，provider不写入项目仓库。 (Human accepted the durability and concurrency settings.)
- Q: SQLite StateStore如何初始化与处理schema版本？ → 采用幂等bootstrap：首次打开创建state_events与state_metadata，metadata保存schema_version；支持版本正常打开，遇到更高或不支持版本fail-closed；本轮不引入复杂migration framework，后续版本通过显式迁移函数与测试升级。 (Human accepted fail-closed schema bootstrap.)
- Q: StateStore中的事件时间与排序如何定义？ → revision是唯一canonical全局顺序；created_at由StateStore provider记录；occurred_at由节点提供，仅作业务时间与审计信息，不参与排序；同一event_id重试保持原revision，不重新排序。 (Human accepted provider-assigned ordering.)
- Q: StateStore如何处理事件payload与未知event_type？ → StateStore只校验通用事件envelope、JSON可序列化、network/event/aggregate、时间与CAS约束，payload_json保持opaque；Enrollment、Graph、Credential等typed adapter负责业务schema与projection。未知event_type可存储，但不能被不认识它的projection解释。 (Human accepted generic envelope validation.)
- Q: StateStore写入是否强制携带授权上下文？ → 强制。Agent写入必须携带经验证的ScopedCredential并匹配network/node/event/task与能力；Human owner的enrollment、revoke和capability ceiling变更使用独立Human-authority context；缺少授权、过期、revoked或scope不匹配在事务前fail-closed。SQLite文件权限只属于部署防线，不能代替协议授权，Relay只转发不授予权限。 (Human accepted authorization at the StateStore boundary.)
- Q: SQLite StateStore的数据库文件由谁打开？ → 采用独立StateStore service进程独占SQLite文件；Codex与Workbuddy不直接读写数据库，通过provider-neutral typed API访问。MVP可先本机部署，未来跨设备只替换service/provider，不改变Agent协议。 (Human accepted the independent StateStore service boundary.)
- Q: StateStore service的MVP传输协议是什么？ → 采用loopback HTTP/JSON over mTLS：API保持typed HTTP/JSON契约，本机也不因loopback而默认信任进程；Node Identity与ScopedCredential共同参与认证授权。Unix socket作为未来本机优化，不作为第一版协议。 (Human accepted HTTP/JSON over mTLS.)
- Q: StateStore请求如何组合mTLS身份与运行时授权？ → 采用双层授权：mTLS client certificate绑定node_id，Authorization Bearer ScopedCredential绑定network/event/task/capabilities；service强制校验二者node_id一致，并检查credential有效期、revoked状态和scope。Human-authority操作使用独立Human approval context，不能伪装成Agent credential。 (Human accepted dual-layer request authorization.)
- Q: MVP ScopedCredential采用什么形态？ → 采用短期opaque bearer token：StateStore生成高熵随机token，仅保存token hash与绑定的network/node/event/task/capabilities/issued_at/expires_at metadata；请求通过Authorization header携带，service同时校验mTLS node、hash、scope、expiry与revoke。未来离线验证再增加Ed25519/JWS provider，不让MVP过早绑定JWT。 (Human accepted opaque short-lived credentials.)
- Q: SQLite StateStore第一条TDD纵切包含哪些验收？ → 限定为真实better-sqlite3 provider的本地typed API：幂等bootstrap与schema version、getRevision、network-level CAS append、同event_id duplicate、revision conflict、按revision readEvents，以及WAL/事务/synchronous=FULL配置验证。本条不包含HTTP service、mTLS、credential endpoint、ArtifactStore和Relay。 (Human accepted the narrow StateStore provider tracer slice.)
- Q: StateStore typed API如何区分正常结果与错误？ → 采用结构化正常结果：recorded、duplicate、conflict；输入不合法返回明确validation error；SQLite I/O、损坏或不兼容schema返回blocked/failure。CAS conflict不自动重试，duplicate不改revision。 (Human accepted explicit result semantics.)
- Q: StateStore readEvents是否返回一致性快照revision？ → 采用一致性read transaction并返回snapshot_revision；事件全部不超过该revision，支持after_revision增量读取；调用方记录该revision用于context/evidence，多次读取需显式接受新snapshot，不隐式假设跨读取一致。 (Human accepted snapshot revision semantics.)
- Q: SQLite StateStore MVP是否实现复制与自动备份？ → 暂不实现。MVP保证单实例SQLite事务持久化和启动完整性检查，不做多副本、跨设备同步、自动failover，也不把WAL当复制协议；预留backup/restore provider接口。StateStore丢失进入network-recovery-blocked，不能自动重建owner或权限。 (Human accepted deferred StateStore replication and backup.)
- Q: StateStore事件是否保存payload hash？ → 采用。append时对canonical JSON payload计算SHA-256并随事件保存；readEvents可验证hash，发现不一致返回blocked。payload hash只用于存储完整性与迁移校验，不替代Human/Node签名，也不宣称能防御直接写数据库文件的攻击者。 (Human accepted payload integrity hashing.)
- Q: payload_sha256采用什么canonical JSON规则？ → 采用递归字典序对象key、数组保序、无空白JSON；拒绝undefined、NaN、Infinity、函数和循环引用，只接受JSON-compatible payload；按UTF-8计算SHA-256，读时使用同一canonicalizer验证。 (Human accepted deterministic payload canonicalization.)
- Q: StateStore单个payload_json的大小上限是多少？ → 采用默认256 KiB上限；超出直接validation error，不截断或隐式压缩。大型Evidence、日志、checkpoint与二进制进入ArtifactStore，StateStore只保存artifact id、hash、大小、归属和授权范围。 (Human accepted the bounded StateStore payload size.)
- Q: SQLite StateStore如何持久化network-level当前revision？ → 采用独立network_metadata表：network_id主键、current_revision、schema_version、created_at、updated_at。append在同一事务内锁定metadata、校验expected_revision、写入下一revision的state_events并更新current_revision；不扫描MAX(revision)推断当前revision，数据库schema_version与network revision分离。 (Human accepted the CAS metadata anchor.)
- Q: state_events采用哪些数据库约束与索引？ → 采用network_id+revision主键、network_id+event_id唯一约束、aggregate与revision查询索引、created_at索引；revision为正数，核心字段非空，payload_sha256为64位小写hex；数据库层禁止更新与删除事件，强化append-only语义。 (Human accepted append-only database constraints.)
- Q: SQLite provider与StateStore service如何分层授权？ → better-sqlite3 provider第一条纵切只负责事务、CAS、dedupe、完整性与append-only；StateStore service/API负责mTLS、ScopedCredential、Human-authority context与revoke校验。provider接受已验证typed request，不解析Bearer token；未来可注入AuthorizationVerifier但不把HTTP credential语义硬编码进SQLite。 (Human accepted provider/service authorization separation.)
- Q: SQLite CAS append采用什么事务锁模式？ → 采用显式BEGIN IMMEDIATE：append开始即获取写锁，在同一事务内读取network_metadata、校验expected_revision、写event并更新revision；锁竞争使用busy_timeout，CAS不匹配返回conflict，应用层不自动重试。 (Human accepted immediate transaction locking.)
- Q: Network如何创建并获得初始revision？ → 采用显式createNetwork流程：只有Human-authority context能创建network；事务内创建network_metadata并追加network.created事件，revision为1；普通Agent append不能隐式创建network，不存在network返回network-not-found。 (Human accepted explicit Human-owned network creation.)
- Q: Network是否允许物理删除？ → 不允许物理删除；采用Human-authority的network.archived tombstone作为最后生命周期事件。archived后拒绝新Agent事件、credential与enrollment，只允许只读审计与recovery查询；恢复必须由Human明确执行，物理清理留给未来retention策略。 (Human accepted append-only network archival.)
- Q: StateStore service第一版HTTP API包含哪些端点？ → 限定为GET /healthz、POST /v1/networks、GET /v1/networks/:id/revision、POST /v1/networks/:id/events、GET /v1/networks/:id/events?after_revision；不加入ArtifactStore、Relay、watch/long-poll、SQL或任意查询。除health外均经过mTLS与授权上下文，事件端点只接受通用envelope。 (Human accepted the narrow StateStore HTTP API.)
- Q: StateStore healthz是否免认证？ → 采用免认证healthz：只返回service/schema/status，不返回network、owner、revision、节点或credential信息，并声明side_effects_executed=false；其他所有endpoint强制mTLS与授权。 (Human accepted minimal unauthenticated health probe.)
- Q: HTTP service如何接入opaque credential验证？ → 当前HTTP API不公开credential签发endpoint；service构造时注入provider-neutral CredentialVerifier，根据opaque token hash查询credential metadata并验证scope/expiry/revoke。测试可用内存verifier，后续独立slice实现真实token生成、hash存储、renew/revoke；service不自行扩大scope或代表Human签发权限。 (Human accepted injected credential verification.)
- Q: mTLS peer certificate如何映射Node Identity？ → 从TLS peer certificate原始DER bytes计算SHA-256作为node_id；必须匹配已注册enrollment projection，拒绝仅凭CN、Subject、display name或客户端自报node_id；certificate未注册或已revoked直接拒绝；CredentialVerifier返回的node_id必须与mTLS fingerprint一致。 (Human accepted certificate-derived node identity.)
- Q: StateStore service是否拥有独立Service Identity？ → 采用独立X.509 service certificate/key；service不代表任何Agent、不成为Center Node。客户端通过pinned service certificate/CA验证服务端，service通过客户端证书fingerprint验证Agent Node Identity；MVP由启动配置提供service trust material，后续再纳入Human-controlled rotation。 (Human accepted separate StateStore service identity.)
- Q: MVP StateStore service如何建立服务端TLS信任？ → 采用pinned self-signed service certificate：Agent client显式配置service certificate作为trust material，不使用通用CA、系统trust store或自动发现；service certificate轮换需显式更新pin，失败进入blocked。未来跨设备规模化再引入Network CA/Service Authority。 (Human accepted pinned service certificate trust.)
- Q: MVP StateStore service监听在哪个网络边界？ → 默认只bind 127.0.0.1，不监听0.0.0.0，不做LAN discovery、端口映射或Relay暴露；端口由调用方配置。即使loopback仍强制mTLS与Bearer授权，跨设备访问留给后续transport slice。 (Human accepted loopback-only service binding.)
- Q: StateStore service采用什么HTTP实现？ → 采用Node原生https.createServer，不引入Express/Fastify；手写最小路由与JSON body解析，TLS参数显式传入，复用现有原生HTTP server风格，未来通过adapter扩展而不改变typed API。 (Human accepted native HTTPS service implementation.)
- Q: StateStore service的HTTP body大小边界是什么？ → HTTP request body上限512 KiB，超出返回413；JSON解析失败返回400；StateStore payload仍硬限制256 KiB并返回domain validation error；不截断、不自动压缩、不写临时文件，大响应未来转ArtifactStore。 (Human accepted two-level request size limits.)
- Q: StateStore service的HTTP错误响应如何结构化？ → 统一返回zj-loop.state_store_http.v1结构：status、reason、side_effects_executed=false；400输入错误、401缺少/无效认证、403无权限或revoked、404 network不存在、409 CAS或event冲突、413超限、500/503 provider故障；不返回token、私钥、完整证书或敏感payload。 (Human accepted structured StateStore HTTP errors.)
- Q: CredentialVerifier采用什么provider-neutral接口？ → 采用verify({token,node_id,network_id,operation,event_id?,task_id?,required_capabilities?})，返回allowed或blocked及reason。service从mTLS证书得到node_id，从URL/body映射network与任务scope，从method/path映射operation；verifier负责token hash、expiry、revoked、node、scope与capability校验，service不解析token或直接读取credential表。 (Human accepted the injected verifier contract.)
- Q: Human-authority HTTP请求如何区别于Agent Bearer credential？ → 采用独立X-ZJ-Loop-Human-Approval签名上下文：Agent Bearer只允许事件范围内操作；创建network、revoke和capability ceiling变更必须携带绑定human_id、action/network、request digest、issued_at、expires_at的Human context，由注入HumanAuthorityVerifier验证。MVP可用内存fixture，后续接Human-held signing key/UI。 (Human accepted separate Human authority context.)
- Q: POST /v1/networks的owner_id从哪里获得？ → 请求body只接受network_id，不接受owner_id；owner_id只来自已验证Human-authority context。service将verifier返回的human_id写入network_metadata.owner_id；Human context的request digest覆盖完整body，body出现owner_id直接拒绝。 (Human accepted verifier-derived owner binding.)
- Q: Human approval context由谁解析？ → X-ZJ-Loop-Human-Approval作为opaque context传给注入的HumanAuthorityVerifier；verifier负责解析、验签、有效期与action/body digest校验，返回human_id或blocked。service只读header、限制长度、传递action/body并使用verifier结果，不绑定签名算法或key格式。 (Human accepted opaque Human verifier context.)
- Q: 真实ScopedCredential provider的MVP实现采用什么形态？ → 采用独立SQLite credential provider：首次签发生成一次性高熵opaque bearer token，仅持久化SHA-256 token hash及network/node/event/task/capabilities/issued_at/expires_at/revoked_at元数据；通过CredentialVerifier注入StateStore service，按mTLS node_id、scope、expiry和revoke fail-closed验证。 (Human accepted the provider boundary; credential issuance/revoke endpoint and Human-held signing context remain later work.)
- Q: ArtifactStore第一条provider纵切采用什么形态？ → 采用本地content-addressed文件目录：artifact_id为sha256内容摘要，文件与metadata sidecar原子创建，读取时校验network归属、大小、content_type与内容hash；StateStore只保存artifact引用，ArtifactStore不进入HTTP service与Relay。 (Human accepted local immutable artifact provider as the second implementation slice.)
- Q: Relay接受MessageEvent后的持久性边界是什么？ → 采用StateStore作为唯一canonical MessageEvent事实源：只有StateStore成功记录事件后Relay才返回publish accepted；Relay只负责短期投递、唤醒、重试和连接管理，重启后消费者依据cursor从StateStore按revision恢复，允许重复投递但不能丢失已记录事件。 (Human confirmed Relay is transport, not a second message database.)
- Q: Relay的投递确认ack代表什么？ → 采用at-least-once投递：ack只表示消费者已完成身份/权限校验并将事件写入可恢复执行入口；消费者先记录delivery_accepted等canonical execution状态再ack，未ack可重试，已ack但中断由StateStore recovery处理，执行完成/验证/Review Handoff另行记录，不存在ack=completed。 (Human confirmed transport acceptance is distinct from business completion.)
- Q: Relay的订阅与恢复cursor绑定什么？ → 采用network_id + consumer_node_id + last_accepted_revision；cursor使用StateStore的network revision而非Relay本地sequence，消费者成功写入delivery_accepted等canonical状态后才推进cursor，重连从after_revision=last_accepted_revision恢复并允许重复投递。 (Human confirmed recovery position belongs to the StateStore revision domain.)
- Q: Relay允许转发什么内容？ → 采用Relay只转发已写入StateStore的canonical MessageEvent引用和受限投递envelope；不接受绕过StateStore的任意消息，不创建/修改事件、不授予或扩大capability、不改写目标依赖权限，不承载大型日志、checkpoint或二进制，后者使用ArtifactStore引用。 (Human confirmed Relay is transport-only and cannot bypass canonical facts or authority.)
- Q: Relay失败时如何重试与停止？ → 采用仅对明确临时连接/超时故障做有限指数退避：最多5次，建议1s、2s、4s、8s、16s并加jitter；认证失败、权限不足、revoked、事件冲突和协议校验失败立即停止；超过上限写入delivery_blocked或transport-recovery-required，不自动续签credential、改变目标节点或无限重试，恢复需中心责任单元或Human明确发起。 (Human confirmed bounded retry and explainable stop.)
- Q: Relay如何决定MessageEvent投递目标节点？ → 采用Directed Task Graph显式指定assigned_node，Relay不根据能力、在线状态或订阅兴趣自动选节点；单task单目标，多节点协作通过多个有依赖task或显式fan-out，每个目标节点独立delivery_id和ack生命周期；目标变更由中心责任单元重新编排并产生新事实。 (Human confirmed Relay cannot invent or rewrite task assignment.)
- Q: Relay的MVP连接模型是什么？ → 采用HTTP/JSON long-poll：Agent通过mTLS与短期scoped session credential建立Relay session，按session发起long-poll获取授权delivery并显式ack，超时返回空结果；断线后使用last_accepted_revision恢复。不引入WebSocket、WebRTC或P2P，未来可增加transport adapter而不改变canonical协议。 (Human confirmed HTTP long-poll as the first Relay transport.)
- Q: Relay session的生命周期和凭证绑定如何定义？ → 采用短期、无权力扩张的session，绑定network_id + node_id + credential scope；session不取代ScopedCredential也不独立授予权限，TTL不超过credential剩余有效期且MVP上限建议15分钟；credential revoke/过期立即拒绝新long-poll与ack，不自动续签或转移session，重建session不改变StateStore cursor，session_id为随机opaque标识。 (Human confirmed Relay session is ephemeral connection state, not authority.)
- Q: Producer如何触发Relay投递？ → 采用Producer先通过StateStore append MessageEvent，Relay不提供创建事件的publish API；Relay通过StateStore revision/cursor发现新事件，再依据已存在的Directed Task Graph assigned_node生成delivery。事件创建只有StateStore入口，Relay不承担CAS、event dedupe或Graph真相。 (Human confirmed StateStore append is the sole event creation path.)
- Q: Relay如何确认目标节点合法而不解释Directed Task Graph？ → 采用注入的provider-neutral DeliveryResolver：由StateStore/Graph projection或中心编排层返回已验证的delivery target，Relay不实现Graph解析。Relay只校验event/revision存在、target与session node一致、network/task生命周期有效和credential具备投递/消费能力；Resolver blocked则停止投递并记录原因。 (Human confirmed Graph authority stays outside the transport service.)
- Q: Relay的delivery状态存在哪里？ → 采用所有对恢复、审计和责任有意义的delivery状态写入StateStore，Relay内存只保留可丢弃连接/缓存；canonical状态包括delivery.offered、delivery.retry_scheduled、delivery.accepted、delivery.blocked和delivery.acknowledged，acknowledged只表示传输确认。Relay可用受限transport authority写这些事实，但不能修改MessageEvent、Directed Task Graph、CapabilityGrant、Human decision或Execution/Evidence业务结论。 (Human confirmed delivery observability belongs to StateStore without granting Relay business authority.)
- Q: Relay的transport authority具体允许写什么？ → 采用独立service identity与受限transport credential，只能在指定network内追加固定delivery事件：delivery.offered、delivery.retry_scheduled、delivery.accepted、delivery.blocked、delivery.acknowledged；记录必须绑定network/event/task/delivery/target和重试上下文；禁止修改删除历史、写Human decision/CapabilityGrant/Execution completed/Evidence accepted、改变目标或替代Human authority。 (Human confirmed Relay transport authority is append-only and event-type constrained.)
- Q: 如何避免同一delivery的并发投递、重复ack或状态倒退？ → 采用delivery_id幂等键与StateStore network-level CAS结合的delivery状态机；每次尝试有attempt_id，相同状态重试返回duplicate，非法倒退或并发冲突返回conflict；Relay可重复投递，消费者按delivery_id/task_id幂等，delivery状态与业务Execution状态分离，冲突进入delivery-conflict并解释原因。 (Human confirmed transport concurrency cannot overwrite canonical lifecycle.)
- Q: Relay的日志和可观测性允许记录什么？ → 采用只记录可审计元数据：network/event/task/delivery/attempt、source/target node、revision、状态、重试次数、错误码、payload/artifact hash、时间戳和协议版本；禁止Bearer token、Human approval context、私钥、完整证书、完整payload、日志正文、checkpoint或二进制。日志非canonical truth，关键delivery状态仍写StateStore。 (Human confirmed Relay observability is metadata-only.)
- Q: Relay服务身份和客户端信任如何建立？ → 采用Relay独立service identity与显式pinned X.509 certificate；Agent客户端显式pin Relay证书，Relay要求Agent mTLS client certificate并从DER计算node_id。不使用系统CA、通用trust store或自动发现，不因loopback省略mTLS；证书轮换需Human/部署显式更新pin，Relay不代表Agent也不成为Center Node，Relay与StateStore服务身份独立。 (Human confirmed independent pinned Relay trust.)
- Q: Relay是否必须是独立进程以及如何隔离Agent资源？ → 采用独立Relay service process，仅通过mTLS+HTTP/JSON与Agent通信；Relay不加载Agent工作区、不执行任务、不共享Agent内存或IPC状态、不checkout或读写目标repo、不持有Agent工作目录、token明文或执行上下文；Relay重启不改变Agent worktree、Execution或StateStore canonical facts。 (Human confirmed process and external-resource isolation.)
- Q: Relay关闭、重启或StateStore不可用时系统呈现什么状态？ → 采用显式transport-degraded或state-store-unavailable，不伪装成功，也不使用绕过StateStore的本地canonical队列；Relay重启从StateStore恢复未ack delivery，暂时不可用时事件保持pending，有限重试后进入transport-recovery-required；StateStore不可用时禁止创建事件、ack或推进cursor；运行中task不被Relay强行终止，但新生命周期/Evidence写入需明确blocked或待恢复，恢复留下新事实。 (Human confirmed transport failure is explainable and cannot bypass StateStore.)
- Q: 单次delivery的超时、租约和重投如何定义？ → 采用delivery_id不变、attempt_id每次重投递新建的有限lease；MVP offer/long-poll返回后ack lease建议30秒，未ack到期记录delivery.retry_scheduled并按退避重投；ack关闭当前lease，旧attempt迟到ack返回duplicate/stale且不得倒退，业务执行超时由Node Runtime/Execution生命周期负责。 (Human confirmed Relay lease is transport-level, not execution timeout.)
- Q: long-poll请求的超时、空响应和并发连接上限如何定义？ → 采用单次long-poll最长25秒；无delivery返回204或结构化空结果；每session同时只允许一个long-poll，并发请求返回session-request-in-progress；每次最多返回一个delivery以简化ack/lease；客户端空响应后带jitter重连，Relay不无限保留连接或内存队列。 (Human confirmed bounded long-poll behavior.)
- Q: Relay是否负责节点enrollment？ → 采用Relay不负责enrollment，也不能自行接纳新节点；只有Human authority批准、StateStore存在enrollment projection且拥有有效ScopedCredential的节点才能建立Relay session。session创建不等于enrollment，enrollment/revoke/re-enrollment由StateStore/Human authority完成，revoke后立即阻止新session、long-poll和ack，Relay只消费验证结果而不复制权限真相。 (Human confirmed enrollment authority remains outside Relay.)
- Q: 节点revoke后已建立session和active delivery如何处理？ → 采用revoke立即失效session后续权限并终止未完成transport lease，不强杀已开始业务Execution；active long-poll结束，未ack delivery停止重投并写delivery.blocked，迟到ack返回credential-revoked且不改变状态；被撤销节点不能领取新事件、读取新Artifact或续签credential，恢复需Human发起re-enrollment/新credential。 (Human confirmed revoke blocks transport without pretending to undo running work.)
- Q: 目标节点离线时Relay是否自动改派任务？ → 采用Relay不自动改派；目标离线只做有限重试，超限进入transport-recovery-required，原task assigned_node保持不变。改派由Human或Human+Agent中心责任单元重新评估并创建新task/execution或显式recovery action，保留原delivery失败证据，不覆盖原task，Relay不静默改变责任归属。 (Human confirmed offline delivery cannot silently change accountability.)
- Q: Relay MVP暴露哪些HTTP endpoint？ → 采用最小HTTP集合：GET /healthz、POST /v1/sessions、DELETE /v1/sessions/:session_id、GET /v1/sessions/:session_id/deliveries、POST /v1/sessions/:session_id/deliveries/:delivery_id/ack、GET /v1/sessions/:session_id/status。明确不暴露publish/任意消息创建、enrollment、credential签发、Graph编排、task完成、Evidence接受、Human decision、SQL任意查询或大文件上传接口。 (Human confirmed the narrow Relay HTTP surface.)
- Q: Relay HTTP response/error schema如何定义？ → 采用独立zj-loop.relay_http.v1 schema；正常响应包含schema/status/side_effects_executed及必要session/delivery/cursor；错误固定映射400请求或cursor无效、401缺认证、403revoked/scope/target不符、404资源不存在、409并发/CAS/重复或过期ack、410session/lease过期、413envelope超限、429并发/速率限制、503StateStore或Resolver不可用；不返回秘密或敏感payload。 (Human confirmed structured Relay protocol errors.)
- Q: Relay delivery envelope大小和payload传输限制是什么？ → 采用Relay HTTP body上限64KiB、delivery envelope上限32KiB；只允许小型结构化元数据和Artifact引用，不携带大型payload、日志、checkpoint或二进制。完整MessageEvent payload由消费者按权限从StateStore读取，Artifact内容由消费者按权限从ArtifactStore读取；超限返回413且不截断、压缩或临时转存。 (Human confirmed Relay carries references, not data bulk.)
- Q: delivery中的事件和Artifact内容由谁读取？ → 采用Relay只返回引用；消费者使用自己的scoped credential直接从StateStore读取MessageEvent、从ArtifactStore读取Artifact，Relay不做代理读取或数据中转。StateStore/ArtifactStore各自执行权限校验，读取失败由消费者记录为execution blocked或recovery required。 (Human confirmed Relay does not become a data access proxy.)
- Q: Relay envelope如何防止引用被篡改或错配？ → 采用envelope携带network_id、event_id、revision、task_id、delivery_id、target_node_id，Relay生成envelope_sha256；消费者从StateStore校验event的network/event/revision/task绑定，从ArtifactStore校验artifact_id/content_sha256/network归属；任一不一致进入delivery-integrity-failed且不ack。envelope hash只做完整性校验，不替代mTLS、credential或Human authority。 (Human confirmed reference integrity is verified at both transport and resource boundaries.)
- Q: Relay是否保证事件顺序？ → 采用Relay不提供全局顺序保证；唯一canonical顺序是StateStore network revision，Directed Task Graph依赖顺序由中心编排/Node Runtime校验。Relay可按revision尽力投递但不同task/target可并行，依赖未满足时消费者不ack或记录delivery-dependency-blocked，Relay不重排、跳过或补造依赖。 (Human confirmed business ordering belongs to Graph/Execution, not transport.)
- Q: Relay的背压和资源上限如何定义？ → 采用每session最多一个active long-poll、每node最多一个active session，全局active session由部署配置限制；内存只保留连接与有限delivery metadata，不缓存完整payload；超限返回429 relay-capacity-exceeded，不丢弃已写StateStore事件，只延迟投递，恢复按StateStore cursor继续，不使用无限内存队列。 (Human confirmed bounded transport capacity and durable recovery.)
- Q: 消费者取消断开或拒绝delivery时如何区分transport与business execution？ → 采用连接断开仅为transport事件，不等于业务取消；中断long-poll的attempt等待lease到期或按断开处理后可重投；能力/依赖不满足不ack成功并记录delivery.blocked，明确拒绝记录transport-level delivery.rejected；task/execution cancel必须由中心责任单元或Human写StateStore，Relay不能把断开/超时/拒绝自动解释成业务失败或取消。 (Human confirmed transport interruption cannot decide business responsibility.)

- Q: Relay如何优雅停机？ → 采用draining流程：先将readyz置为not ready，停止新session和新delivery lease；已建立long-poll返回503 relay-draining，已发delivery等待ack lease自然完成或记录retry；宽限期后关闭连接。重启从StateStore恢复未ack delivery，停机写relay.draining/relay.stopped运维事实但不修改业务Execution。 (Human confirmed graceful shutdown and restart recovery.)
